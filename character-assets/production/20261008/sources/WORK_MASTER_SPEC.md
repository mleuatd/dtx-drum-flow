# DTX Drum Flow — Work実行用・女の子のドラム演奏差分画像 制作仕様書

**版:** 2026-10-08 v2／**文書の役割:** Workに添付してそのまま順次制作を実施させるための作業指示書。新規描き起こしの発注書ではない。  
**優先順位:** この仕様書 > 同梱素材の真正性 > リポジトリの現行正式採用素材・台帳（衝突は保護して記録） > 以前の仕様書（参考）。  
**最も重要な原則:** 同梱動画の「同じ女の子」を既存ドラムの後ろ／前に一貫して配置し、必要な打撃ポーズを作る。承認済みのドラムの線を変更しない。必要な部分だけを編集する。ユーザーに毎画像の作図指示を求めない。

## 0. 最初に必ず理解すること
- 成果は説明文や進捗表だけでなく、**実際のHit／Rebound透過PNG画像の完成**。各動作の「Hit＝叩いた瞬間」「Rebound＝叩いた直後の自然な跳ね返り」を**必ずペア**で扱う。
- 動作数を先に決めつけない。過去の30動作・60枚は参考値であり、最新版のアプリ実装・動作リスト・正式素材を調べた後に確定する。
- 同梱動画は**キャラクターの外見・身体比率・服装・髪型・複数方向の形状の一次参照**。動画から見えない骨や関節位置は推定値で、医学的骨格の正解ではない。動画に実際のドラム演奏が映っていないなら、演奏姿勢はドラムの位置と既存の作例・身体の可動域から**推定して設計**する。映っていない打撃動作を「動画から観察した」と表現しない。
- 参考動画の画風をそのまま画像に貼るのではなく、**女の子の同一性を維持して、既存の手描き鉛筆ラフ線画へ翻案**する。ただし既存の承認済みNeutral・部分レイヤーを勝手に全身描き直さない。
- 「画像生成AIで女の子全体を再生成してそれらしくする」は禁止。使用できる編集は、既存人物レイヤーと動画に基づく位置決め・線抽出・局所トレース・部位変形・再接続・差分描線など、**固定領域と同一人物性を検証できるもの**。必要な参照素材が不足する場合は勝手に別の少女を生み出さず、何が不足か記録して進められる別動作を進行する。

## 3. 女の子の動画から最初に作るキャラクター設定資料
1. 動画の長さ・解像度・フレームレート・向き・カット境界を確認し、**正面／左右斜め／側面／後方**で使える代表フレームを取得。十分な視認性のある画面を選び、ゲームUIなど周辺映り込みを不要なら除外する。抽出フレームには**タイムコード**を記録。
2. 髪（前髪・後髪・毛先・分け目）、顔輪郭、首、肩幅、胴、腰、肘、手首、腿、膝、足首、服の袖・裾・靴、アクセサリの有無を**見える範囲で観察記録**。動画から確定できない情報と推定を分ける。
3. キャラ骨格は**2D関節アンカー＋可動域のモデル**として表現する。肩・肘・手首・握り・左右スティック先端、首・腰・膝・足首など。体格比・線画での腕長・脚長と、座位での可動域を整合させる。動画だけから3D人体モデルの精度を保証しない。
4. 既存の承認済み人物Neutralが見つかれば、そちらの**キャンバス上の座標と描線**を優先し、動画はキャラクター一貫性の照合に使う。見つからなければ「暫定Neutral案」と記し、必要なら全体の基礎人物レイヤー作成の可否を明示する（許可のない自由なAI新規生成は禁止）。
5. `character_reference.md`、時間付き画像一覧、`skeleton_landmarks.json`（座標とconfidence・根拠タイムコード・推定理由）を保存する。足りない座標は推定として明示する。

## 4. 固定ドラムとの合成条件
- 基準キャンバスは**1448×1086 px**、PNGの**RGBA透過あり**。作業画像は元ドラムとの**左上 (0,0)、等倍・無回転**配置を守る。
- **ドラムのピクセルは一切編集しない。** 回転、移動、拡大縮小、描線補正、楽器追加、クロップ、背景白埋め等は禁止。
- **固定ドラムの背後に人物を置く部分／ドラムの前を腕やスティックが横切る部分**は、前後関係に応じてマスクや複数合成層で扱う。単純に人物全体を常に前面に置いて不自然な隠れを作らない。合成順は完成画で判断し、原画自体は不変。
- 元画像左のHH、上の複数シンバル、中央タム、前面のSN/BD、右のFTなど、**打撃対象ごとに先端が何に触れるか**をドラムの座標から明示する。各レーンの名称・左右割当は最新版コード・素材定義に一致させる。楽器位置を想像で変えない。
- **静止したドラムは背景レイヤーとして別途維持する。** 最終出力が人物のみ透過レイヤーの場合でも、QA用合成版では常に今回の固定ドラムを使用する。

## 5. 線画スタイル・禁止事項
- **白黒シャープペンシルの素人っぽいラフ線画**。細い黒／灰の線を短く分割し、何度も重ね書きした手描き感を残す。輪郭を一筆できれいに整えすぎない。**着色・黒ベタ・面塗り・なめらかな清書線・不要な陰影追加は禁止**。
- 「動画を正確に模写する」ことと「ラフ線画化」を両立し、髪型・服の特徴・顔の向き・体格を不意に変更しない。同一人物に見えない差分は不合格。
- 動作差分以外の頭・胴・椅子・無関係の手足を原則不変とする。**肩～肘～手首～手～スティック**、ペダル動作なら腰～膝～足首～足の可動範囲だけを局所修正する。局所修正に必要な短い線追加・削除は可。
- 腕・手・スティックの本数増殖、関節の不連続、浮いた握り、楽器のすり抜け、左右逆、服装変更、動画と異なる頭身、ペダル位置不一致は不合格。

## 6. HitとReboundをどう設計するか
- 必要な動作を最新実装と原画から洗い出し、`motion_id / 楽器 / 手足 / Hit打点 / neutral関節 / hit関節 / rebound関節 / 使用donor` の対応表を作成する。初期30動作・60枚は**数の目安**にすぎない。
- Hitでは、指定の**スティック先端が対象打面に実際に届く**。Reboundでは打点からスティックが離れ、同じ身体構造のまま自然に戻る。両者で頭や体幹が急に動いたり、腕の長さが変わったりしない。
- 必要なら打面法線と肘・手首の関節弧を推定。打撃時刻の画像だけでは速度やフォームの「唯一の正解」は決まらないため、**物理的にもっともらしく映像間で連続すること**を検証基準にする。
- 片手・両手・キック・同時打撃を区別し、**一人の女の子の一つの姿勢**として成立させる。単独画像を全身合成して腕が4本になる等は不可。
- Neutral → Hit → Rebound → NeutralをGIF/連続プレビューで表示。HitとReboundが同一画像・意味のない微小ずれなら不合格。

## 7. 具体的な制作順序（Workは作業ごとに自律実行する）
**Phase 0 / 安全確認:** 展開したZIP・動画・原画のSHA-256を照合。接続先最新mainのHEADを記録。全素材を上書き不可の入力として扱う。

**Phase 1 / 調査:** 動画から代表フレームを抽出、キャラクター設定・2D関節モデルを作る。同時に既存の画像・donor・採用台帳・コード中の画像参照を調べる。ドラムと既存人物の重ね合わせで配置を確定。

**Phase 2 / 計画:** 必要動作のマトリクスを作り、採用済み/片側完成/候補/未着手/ブロックに区分。**最初は既存人物・既存donorのある単独打撃1セットを試作**し、固定領域、人体構造、打点、線画の整合を機械・視覚の両方で検査。

**Phase 3 / 一括制作:** 合格の方法を他の動作にも横展開。各セットごとに差分編集 → PNG書き出し → 透過/座標/固定領域/関節・線数チェック → ドラム合成表示 → GIF検証 → 台帳更新 → 次へ。重大な不一致は候補に止め、次の着手可能動作へ。未承認の候補を勝手に正式採用しない。

**Phase 4 / アプリ結合:** 現行の画像パス/manifest/キーを壊さず、必要に応じ実装側への参照を追加。ローカルで画像読み込み・ペア切替・コンボ・透過・404を検査。GitHubに反映する場合は権限と差分を確認し履歴を残す。

**Phase 5 / 納品:** 採用済み・新規完成・候補・失敗・ブロックの動作一覧、PNG、差分マスク、検証用GIF、動画参照フレーム、各種JSON、成果ZIP、残タスクと次回再開手順をまとめる。

## 8. 具体的な品質検証（機械検査だけでは不十分）
- PNGサイズ1448×1086か、アルファあり、透明背景が維持されるか、元ドラムのSHAが変更されていないか。
- 人物レイヤーの(0,0)位置合わせにドリフトはないか。胸・頭・腰・椅子等「変更禁止領域」の差分がゼロまたは定義済み局所修正のみか。
- 指定楽器への打点位置・スティック接触・リバウンド方向、肘/手首の連続性、衣装の一致をチェック。
- 動画の代表フレームと比べ、同一人物と認識できる輪郭と髪/服か。**動画外の部位や見えない側は推定である旨を記録**。
- Neutral/Hit/Reboundの比較GIFで、腕が複製されたり線が飛んだりしないかを目視（または使用可能な視覚評価機能で）確認。プログラム上のPASSだけで終了させない。
- QA不能は `VISUAL_QA_PENDING`、画風に差があるものは `CANDIDATE`、素材不足は `BLOCKED`。**完成数に入れるのは全検査に合格したペアだけ**。

## 9. 台帳・命名・保存
- 実リポジトリの既存命名規則に合わせる。勝手な構造変更はしない。例：`hh/hit_r.png`, `hh/rebound_r.png` は**参考であり正式パスは現物調査で決める**。
- 各動作には `motion_id`, `instrument`, `limbs`, `source_assets`, `hit_path`, `rebound_path`, `status`, `qa_numeric`, `qa_visual`, `reference_video_timecode`, `blocked_reason`, `next_action`, `commit_sha` を持たせる。
- 出力は `work_output/character_model/`, `work_output/variants/`, `work_output/previews/`, `work_output/qa/`, `work_output/ledger/` など、採用前は正式ファイルから分離。**入力の01_referenceは触らない**。
- 停止前に「ここまで作成・合格」「次に作るmotion_id」「不足素材」「どう再開するか」を `work_output/RESUME_HERE.md` に必ず残す。

## 10. 明確な停止・例外処理
- GitHub連携不可、画像編集手段が局所修正に対応しない、採用済み人物Neutralが存在しない等の場合：**何ができないかをファイル名と理由付きで記録**。動画フレーム抽出、2Dアンカー推定、着手可能な前工程は実施する。見かけだけの架空の完成報告は禁止。
- 旧採用画像と今回ドラムの座標や画風が矛盾する場合は**いずれも上書きせず**衝突表を作る。安全に判断できない本質的仕様変更だけユーザーへ確認する。
- 1回のWorkで全作業が終わるとは限らない。**セッションをまたいでも再開できるファイル保存**を優先する。Workに持続的な無制限実行を保証するものではない。

## 11. Workへの最初の実行指示（優先する順序）
1. `README_START_HERE.txt` と本書、`MANIFEST_SHA256.json` を読む。01_referenceの動画・ドラムを確認する。
2. 動画の女の子の体格・服・髪・角度別の違いを抽出、**作画の基準になるキャラクター設定資料を完成**させる。
3. GitHubの既存キャラ原画・採用済みHit/Rebound・マニフェストを探してドラムと整合検査する。
4. 必要な動作の総数・残数を確定し、**最も成功見込みの高い未完成の1ペア**を実際に制作してQAする。
5. 方法が成立すれば残りを順次制作。**調査と仕様書の書き直しだけで終わらないこと**。
6. 合格画像だけ反映、GIFと台帳と`RESUME_HERE.md`を更新。実現できない場合は明確なブロッカーと再開手順を納品する。
